## 1. 실적 가속의 정의를 게이트에 반영 (T60)

**정의(확정)**: 매출액 성장률**과** 영업이익 성장률이 **둘 다** YoY로 가속.

| | 이전 | 이후 |
|---|---|---|
| G1 매출 | `rev_yoy(t) > rev_yoy(t−1)` AND `> 0` | 그대로 |
| G2 영업익 | 흑자 AND `op_yoy(t) > 0` | 흑자 AND **`op_yoy(t) > op_yoy(t−1)`** AND `> 0` |

`> 0`을 함께 요구하는 이유: 빼면 **영업이익 −30% → −10%가 '가속'으로 통과**한다.

**사용자에게 물은 이유** — 단순 구현이 흑전을 통째로 죽인다. `op_yoy`는 부호전환
구간에서 애초에 `None`이라(T25) None을 False로 뭉개면 **흑전 53종목이 에러 없이 탈락**한다.
흑전은 이익 가속의 가장 강한 형태인데 정확히 그것만 사라지는, 최악의 방향으로 틀리는 형태다.

**실측**: 통과 343 → **238** · 판정 불가 91 · 흑전 통과 76 · 발송 80 → 67

`적자축소`는 별도 처리가 필요 없었다 — `op_t <= 0`이라 "흑자" 요건에서 이미 걸린다.

## 2. LLM 분석 — 범위·내용·비용 (A′+B)

### 비용 분석 (사용자 요청)

실측 단가를 두 번 고쳤다. 처음 추정이 틀렸다.

| | 1차 추정 | 실측(25건) |
|---|---|---|
| 캐시 히트 | $0.0271 | **$0.0315** |
| 미스 | $0.0346 | **$0.0363** |
| 캐시 절감 | 22% | **13%** |

**비용의 대부분이 출력**(2,400~2,800토큰)이라 캐싱으로 줄일 폭이 작다.

| 대상 | 분기 비용 | 실링 대비 | 판단 |
|---|---|---|---|
| 66 (구 A안) | $2.08 | 26% | 발송 대상 22종목 누락 |
| **238 (게이트 통과 전부)** | **$7.51** | **63%** | **채택** |
| 1,112 (전체) | $35.07 | 292% | **보류** |

전체를 보류한 이유: 탈락 782종목(70%)에 대한 해석은 "가속하지 않았다"의 재확인이고,
실증도 스코어 90+가 +4.68%p / 60미만이 +0.48%p였다 — 낮은 구간에 비용 70%를 쓰는 셈이다.
시간도 11~17시간이라 Actions 잡 상한을 넘는다.

→ **월 실링 $8 → $12** (238종목 + 여유 140건)

### T72 ★★ 발송 기준과 분석 기준이 갈라져 있었다

알림은 **등급**(★/○), 배치는 **스코어 75+**로 뽑았다.
등급은 스코어와 반영도의 **교차** 판정이라 두 기준이 갈라지면 사이로 빠진다.

**실측: 발송 대상 70종목 중 22종목이 해석 없이 알림만 나갔다.**

```
○ KBI동양철관  스코어 74.9  반영도  3.4   ← 0.1점 차이
○ 롯데케미칼    스코어 68.7  반영도  2.7
○ GKL        스코어 69.3  반영도  1.8
```

**반영도가 낮은 종목이 특히 많이 빠졌다** — 하필 이 시스템이 찾는 구간이다.
어느 쪽도 실패하지 않는다. 배치는 "66종목 완료"로 성공을 보고하고 알림도 정상 발송된다.

→ 선정에 발송 등급을 **무조건 포함**. 수정 후 배치 첫 두 건이 KBI동양철관·제이아이테크
— 정확히 이전에 빠지던 종목들이었다.

**교훈**: "누구에게 알리나"와 "누구를 분석하나"처럼 같은 대상을 가리켜야 하는 두 기준은
반드시 한쪽이 다른 쪽을 포함하도록 **코드로 묶어라.**

### T73 배치는 한 워크플로에서 끝나지 않는다

실측 호출당 **36~56초** · 238종목 = **2.4~3.7시간** vs `disclosure_poll` timeout 15분.
그냥 얹으면 매번 강제 종료되고 진행 상황이 로그에 안 남는다.

→ `--max-seconds`로 **스스로 끊는다.** 멱등이라 여러 실행에 누적된다.
- `disclosure_poll` 480초 — 갓 발표된 종목을 빠르게 해석해 알림에 실린다
- `llm_batch.yml`(신규) 밤 3시간 — 따라잡기 · timeout 200분
- `cancel-in-progress: false` — 겹치면 같은 종목에 돈이 두 번 나간다

### T69 호출이 띄엄띄엄이면 캐시를 매번 놓친다

원래는 텔레그램 질의 때만 분석해 TTL 5분을 매번 넘겼다(4건 중 3건 미스).

### T61 LLM이 값 안쪽에 태그를 흘려 넣는다

`tool_use` + strict 스키마인데도 `one_line_thesis` 334자 중 뒤 207자가

### T64 ★ `overflow-x-auto`가 머리글 고정을 무력화한다
`sticky top-0`을 넣었는데 스크롤하면 머리글이 같이 올라갔다. 클래스는 그대로 있고
빌드·tsc 통과, 경고도 없다.

CSS 사양상 한 축이 `visible`이 아니면 다른 축도 `auto`가 된다 → 그 div가 세로 스크롤
컨테이너가 되는데 높이 제한이 없어 스크롤포트가 안 생긴다. `sticky`는 붙을 곳이 없다.

→ `max-h-[70vh] overflow-auto` + `bg-*` + `z-20`. 같은 패턴의 표가 **셋**이었다.
**눈으로 스크롤해 보기 전엔 절대 안 드러난다.**

## 5. 결과 추적 — 회고 분석과 전망

### 시점 확장
`(1,5,20,60)` → `(-5,0,1,5,20,60)`. 구간 **방향**이 시점마다 다르다:
```
days>0   발표일 종가 → D+N      (발표 후 반응)
days==0  직전 거래일 → 발표일    (당일 등락)
days<0   D−N → 발표일          (발표 전 선반영)
```
뒤집으면 부호가 통째로 반대가 되는데 숫자는 그럴듯하다. 손계산 대조 테스트 8건.
음수 컬럼은 `ret_dm5` — `ret_d-5`는 컬럼명이 될 수 없다.

### T66 ★★ 1위가 음수인데 "가장 컸다"고 말했다

> 초과수익이 가장 컸던 구간은 **발표 후 5일**이다 (중앙값 **−0.73%p**).
> → 확인 후 진입이 위험 대비 유리했다.

`Math.max`는 정확했다. **부호를 안 본 것이 버그다.** 숫자와 문장이 같은 화면에 있는데
**문장이 숫자를 배반한다** — 읽는 사람은 문장을 먼저 믿고, 이건 투자 조언이다.

### T67 표본 부족을 결론으로 바꿔치기하지 않는다
`MIN_SAMPLE=8` 미만이면 결론을 만들지 않고 근거등급(확실/참고/불충분)을 표시.
'불충분'의 action은 전략에서 제외한다.

검증: 렌더된 집계 3건을 파이썬으로 독립 재계산. 2건 소수점까지 일치, 1건은
**내 파이썬이 틀렸다**(스크린 행을 최신으로 안 접어 185/107 vs 화면 175/117).

### 섹터별 실적 + 다음 분기 전망 (T75)
섹터마다 매출·영업이익 **둘 다** — 이번 분기 중앙값 / 섹터 내 사분위 / 전분기 대비 /
**다음 분기 예상 범위** + 주가 이벤트 · 확인 지표 · 주의점.

**손으로 적은 지식에 숫자를 섞지 않았다:**
- `sectorPlaybook.ts` — 이벤트·지표·주의점만. 숫자 금지(적어 두면 낡는다)
- `projectSector()` — 전망값은 실측에서 계산. 중앙값을 하단, 전분기 대비 변화의
  **절반**을 더한 값을 상단으로(평균회귀가 강해 모멘텀을 온전히 연장하지 않는다)

섹터명이 한 글자만 달라도 조용히 기본값이 나온다 — `지주·기타서비스`가 빠져 있었다.

## 6. 링크·공시 (T58, T74)

### T58 DART 회사명 검색 URL은 검색을 하지 않는다
`dsab007/main.do?textCrpNm=회사명`은 200을 주고 검색창에 이름까지 채우지만
**검색을 실행하지 않아 빈 화면**이다. 파라미터 유무 응답의 차이가
`<input value="…">` **24바이트뿐**이고 페이지 JS가 `search()`를 부르지 않는다.

→ `dsaf001/main.do?rcpNo=`(접수번호). 없는 231종목은 링크를 만들지 않는다.
네이버 증권 링크도 추가(텔레그램은 모바일 주소).

### T74 ★★ "재무를 수집했는가"로 "발표했는가"를 판정했다
2분기를 이미 발표한 종목이 미발표로 분류됐다. 같은 화면의 '최근 공시'에는
그 반기보고서 링크가 걸려 있었다.

```
재무 수집 완료         482
공시는 났는데 재무 없음  609   ← 전부 '미발표'로 표시됐다
진짜 미발표             21
진행률 43.4% → 실제 98.1%
```

빠진 종목이 하필 대형주였다 — 대한항공(9.6조)·레인보우로보틱스·삼양식품·리노공업.
"미발표 630개"는 시즌 중이라면 있을 수 있는 값이라, 공시 목록과 나란히 놓기 전까지
드러나지 않는다.

→ 세 상태로 구분. 진행률은 **공시 기준**으로 잰다.
`earnings_disclosures.fiscal_quarter`는 전 행 null이라 **보고서명**에서 분기를 뽑는다.

## 7. 운영 안정성

### T59 ★★ `force-dynamic`은 fetch 캐시를 막지 못한다
게이트를 고쳐 DB가 67이 됐는데 **배포 사이트가 80을 보여줬다.**
`X-Vercel-Cache: MISS`인데도. 범인은 `.next/cache/fetch-cache`의 이틀 전 파일 44개 —
Vercel이 빌드 캐시를 배포 사이에 복원한다.

→ `createClient` **3곳 전부**에 `NO_STORE_OPTIONS`. 페이지용만 고치면 `/api/cost`와
`/api/telegram/lookup`(HermesCall이 호출)이 그대로 낡는다.
**검증은 캐시가 남아 있는 상태에서** 최신값이 나오는 것으로 했다.

### T62 새 컬럼 하나가 수집 잡 전체를 죽인다
`ret_5d` 미적용 상태에서 `price_run --save`가 PGRST204로 크래시했다.
`universe_daily`는 한 잡에서 시세→스크리닝을 이어 돌아 그날 발굴이 통째로 없어질 뻔했다.
조회는 막고 있었는데 **쓰기가 비어 있었다.**
→ `upsert_tolerating_missing_columns()`. 루프 필수(PostgREST는 하나씩만 알려준다).

### T63 cron이 구 코드로 로컬 저장을 덮어쓴다
`disclosure_poll`이 하루 4회 `screener --save`를 돈다. 04:47Z 실행이 아직 푸시하지 않은
옛 게이트로 돌아 로컬 238을 343으로 되돌렸다. 워크플로는 초록색이고 로그도 안 남는다.

### outcome_run — save를 report 앞으로
`collect → report → save` 순서였다. 리포트가 KeyError로 죽으니 **481건 수집분이 통째로
버려졌다.** `collect()`는 종목당 KIS 일봉 1콜(수 분)인데 **출력용 코드**의 버그가 다 날린다.
→ 저장을 먼저 하고 report를 try로 감쌌다. 다음 실행에서 효과를 봤다.

### 검사기가 두 번 뚫렸다
`horizon_column`을 쓰라는 테스트를 붙였는데 또 KeyError가 났다. 테스트가 `{days}`만
검사하고 `{d}`·`{best}`를 놓쳤다. **변수명을 열거하는 검사기는 새 변수명을 영영 못 잡는다.**
→ 정규식으로 바꾸고 검사기 자체를 5가지 입력으로 검증(T54).
