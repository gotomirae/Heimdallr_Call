# 2026-09-25 — Kairos 기업·산업 Telegram 분석 파이프라인

## 요청

Telegram 개인 채팅에 기업명 또는 산업명을 입력하면 자동으로 심층 투자 분석을 접수하고, 최근
3개월 Google Drive·Notion 자료를 우선해 조사한 뒤 신뢰할 수 있는 웹 자료로 보완하며, 기존
분석과의 변경사항·원본 링크를 포함한 결과를 지정 Notion 계층에 쓴다. 진행률과 실패 원인은
같은 Telegram 접수 메시지에 표시한다.

## 한 일

- 기존 구현을 재점검해 기업명·6자리 코드 접수, Supabase 멱등 큐, Codex wake/claim, 진행 메시지,
  Notion 전달과 사용량 중단 재개는 존재하지만 산업명은 종목 부분일치로 거부되며, 운영 DB에
  대상 유형을 저장할 계약이 없음을 확인했다.
- `AnalysisTarget(company|industry)`를 도입하고, KRX `industry`·`sector`와 지정 투자 산업 목록을
  PostgREST `range()` 페이징으로 한 번에 로드했다. 산업은 완전·정규화 일치만 받고, 기업 정확일치를
  제외한 부분일치보다 산업을 우선하게 했다.
- `kairos_requests`에 `request_kind`, `target_name`, `failed` 상태와 대상 형태 제약을 추가하는 멱등
  마이그레이션을 작성했다. DDL 적용 전에도 기존 기업 요청은 구 스키마로 계속 저장하고,
  산업 요청은 가짜 종목코드를 만들지 않고 스키마 미적용 원인을 Telegram으로 회신한다.
- 브리지의 진행 단계를 15/30/50/60/70/85/95%로 나누고, Telegram 편집 오류가 나도 로컬 단계는
  보존하게 했다. `fail --reason`으로 대상 모호·소스 접근·웹 검증·Notion 작성/재조회·예기치 못한
  오류를 Supabase·SQLite·Telegram에 동시 기록하게 했다.
- 기업은 `1. 기업 투자 분석 → 기업명 (코드·시장) → 날짜별 분석`, 산업은
  `2. 산업 투자 분석 → 산업명 → 날짜별 분석`으로 분리했다. 두 경로 모두 직전 완성본과 원본 링크를
  읽고 변경사항을 명시하게 했다.
- Kairos 원본·설치본 스킬을 동시 갱신했고 산업 보고서 참조문서를 추가했다. 기업 Drive 루트를
  `17Kwbq5u7jiFb7jH14ddV0tI8zfyGcCsk`로 정정했고, 신뢰 가능한 공식 웹으로 공백을 채우며 네이버 블로그 등은
  투자자 관점·반대논거로만 쓰고 핵심 수치는 1차 자료로 재검증하게 했다.
- PRD §8.7, 운영 WORKFLOW, DB 스키마, ADR 20, 함정 T188~T189를 같은 계약으로 맞춰다.

## 운영 적용 완료

- 사용자가 Supabase에 `docs/migrations/kairos_requests.sql`을 적용한 뒤 `python -m src.db.init`을 재실행했다.
  운영 ref `drpxciqkbjlruximqbox`, **16/16 테이블**, `request_kind·target_name` **rows=1**, anon **13/13**,
  `kairos_requests` private RLS 차단이 모두 통과했다.
- 리스너 사전점검은 봇 `8933940541`, 허용 채팅 **1**, 기업 **1,376**, 산업 **188** `ready`였다.
  `HeimdallrTelegramListener`·`HeimdallrKairosCollector`는 모두 활성, 1분 주기, 최근 결과 **0**을 확인했다.
- 로컬 큐의 `trigger_thread=01a0b3d1-390f-7301-bd23-be3bdcda4329`와 Kairos heartbeat 대상이 일치한다.
  heartbeat 프롬프트를 기업·산업 재개와 `failed/rejected` 종료 상태까지 알도록 갱신했다.
  현재 큐가 0건이므로 heartbeat `PAUSED`는 정상이다.
- 실행 조건은 PC 전원·Windows 로그인·절전 해제·AC 전원·Codex 데스크톱 실행·인터넷·커넥터 인증이다.
  자세한 조건과 PC 종료 중 24시간 Telegram 보관 한계를 `telegram_bridge/WORKFLOW.md`에 남겼다.
- 실제 Telegram 기업·산업 요청은 사용자의 정식 입력이 아니므로 이 검증 세션에서 임의로 생성하지 않았고,
  Notion 페이지도 작성하지 않았다.

## 최종 인계 요약

- Telegram 1:1 채팅의 기업명·6자리 코드·산업명을 `company|industry`로 명시적으로 분류하며,
  기업명 부분일치가 `반도체` 같은 산업명을 가로채지 않는다. 문장형·전달·그룹·미인증 입력은
  접수하지 않는다.
- 기업은 `1. 기업 투자 분석 → 기업명(코드·시장) → 날짜별 분석`, 산업은
  `2. 산업 투자 분석 → 산업명 → 날짜별 분석`에 저장한다. 같은 대상의 직전 완성본을 먼저 읽고
  변경사항·원본 링크를 새 보고서에 남긴다.
- 현재 판단 자료는 Google Drive·Notion의 최근 3개월 자료를 우선하고, 공식 원문과 신뢰 가능한
  웹 검색으로 공백을 채운다. 네이버 블로그 등은 정확한 링크·작성일을 남기되 관점·반대논거로만
  쓰고 핵심 수치는 1차 자료로 재검증한다.
- Telegram 접수 메시지는 최근 자료·산업·기업·웹·기존 분석·Notion·검증의 7단계를
  15/30/50/60/70/85/95%로 표시한다. 실패는 제한된 원인 코드와 복구 방법을 Supabase·로컬 큐·Telegram에
  남기며, Telegram 편집 오류가 나도 로컬 진행 단계는 보존한다.
- 운영 Supabase 마이그레이션은 적용·검증 완료다. DB **16/16**, typed request contract,
  anon **13/13**, private RLS가 통과했다. 리스너는 전용 봇 `8933940541`, 허용 채팅 **1**,
  기업 **1,376**, 산업 **188** `ready`다.
- Windows의 `HeimdallrTelegramListener`·`HeimdallrKairosCollector`는 모두 활성·1분 주기·최근 결과 **0**이다.
  로컬 큐는 0건, Codex 대상 작업과 재개 heartbeat ID가 일치한다. 큐가 없을 때 heartbeat `PAUSED`는 정상이다.
- 운영에는 PC 전원·Windows `user` 로그인·절전 해제·AC 전원·Codex 데스크톱 실행/로그인·인터넷·
  Drive/Notion 커넥터 인증이 필요하다. 잠금은 괜찮지만 로그아웃·절전·종료 중에는 실행되지 않는다.
  PC 종료 중 Telegram 업데이트는 최대 24시간만 보관되므로 그 이상이면 요청이 유실될 수 있다.
- 회귀 검증은 **939 passed·1 skipped·3 deselected**, Kairos 집중 **20 passed**, 스킬 원본·설치본
  **2/2 valid·트리 동일**이다. 실제 Telegram 입력은 사용자가 `삼성전자`, `005930`, `반도체` 처럼
  허용된 1:1 채팅에 단독 입력하면 다음 종단간 검증이 시작된다. 진행은 `/status`로 확인한다.
