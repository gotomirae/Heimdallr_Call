# 2026-09-07 — LLM 반복 실패 원인 분석과 이벤트 3단계 전환

## 사용자 목표

- 불필요한 유료 실행을 멈추고 성장 가속 종목·산업을 가장 빠르게 찾는 목적에 비용을 집중한다.
- 한 분기 LLM 갱신을 잠정실적, 정기보고서, 정기보고서 뒤 5영업일 리포트 반영의 최대 세 번으로 제한한다.
- 시세·시가총액·PRI 등 매일 변하는 값은 계속 갱신하되 그 변화만으로 LLM을 다시 부르지 않는다.

## 원인 실측

GitHub Actions `llm_batch` 최신 실행 `34056674098` 로그를 확인했다.

- 전체 209종목, 기존 완료 8, 대기 201
- 실제 호출 94회: 성공 1, 실패 93, 미처리 107
- 실패 90건: `입력에 없는 사실 숫자`; 3건: `max_tokens(16384)` 잘림
- 실행 전 월 비용 $14.35 → 종료 $20.8367, 일 상한 120/120
- 전날도 성공 1·실패 93(숫자 87·출력 상한 6)

직접 원인은 2026-09-05 추가한 `--refresh-finalized`의 레거시 fallback이었다. 숫자·발췌 내용이
같아도 수집 `updated_at`이 분석 `created_at`보다 새로우면 200건 가까이를 재분석 대상으로
열었다. 실패는 저장하지 않아 같은 근거가 다음 날 다시 결제됐다. 개별 오류를 catch해 프로세스가
0으로 끝나므로 Actions 잡은 성공으로 보였다.

즉시 비용 차단을 위해 원격 `llm_batch.yml`을 `disabled_manually`로 전환했다. 수집·스크리너·
대시보드 갱신은 중지하지 않았다.

## 구현

1. 자동 LLM 범위를 성장 가속 중 발송 등급 ★·○로 제한했다. 성장 가속·산업 전수는 기존
   결정론적 스크리너와 대시보드가 계속 담당한다.
2. 공시 폴러가 잠정실적 1단계와 정기보고서 2단계를 즉시 처리한다.
3. 매일 컨센서스 수집 뒤, 정기보고서 공시 후 실제 KOSPI 세션 5일이 모두 지난 ★·○만
   3단계 후보로 검사한다. 공시일 snapshot과 창 종료 snapshot의 연간·향후 분기 컨센서스가
   실제로 달라진 경우만 LLM을 호출한다. 주가만 움직여도 달라지는 PER·선행 PER은 증거에서
   제외한다. 커버리지·변화가 없으면 호출 없이 창을 닫는다.
4. 리포트 원문 수집기는 없으므로 3단계를 원문 분석이라고 부르지 않고
   `naver_wisereport_consensus` 변경이라는 한계를 입력·문서에 명시했다.
5. 실패에도 `(analysis_stage, evidence_hash)`를 저장해 동일 근거 자동 재시도를 막았다.
   새 잠정·확정·컨센서스 근거가 생기면 단계 또는 hash가 달라져 다시 열린다.
6. 운영 성공 응답의 미근거 사실 숫자는 그 토큰만 제거하고 정성 해석은 보존한다. 제거 목록을
   메타와 화면에 표시한다. Canary는 Provider 원품질 비교를 위해 계속 엄격 거부한다.
7. `llm_batch.yml` 예약 스케줄은 삭제하고 ★·○ 수동 장애 복구 전용으로 남겼다.
