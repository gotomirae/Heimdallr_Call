### 시즌 게이팅

GitHub Actions cron은 조건부로 못 쓴다. 두 스케줄을 다 걸고 잡 안에서 판정한다:

```
SEASON_MODE=on   15분스케줄 → 실행
SEASON_MODE=off  15분스케줄 → 건너뜀
SEASON_MODE=미설정 15분스케줄 → 건너뜀   ← 안전한 쪽으로 떨어진다
```

## ★ T47 — 주기를 정하기 전에 월 분을 계산하라

`telegram_listen`을 아무 생각 없이 "5분마다"로 잡았다. 계산해 보니:

```
5분 주기 = 12 × 24 × 30 = 8,640회 = 월 8,640분
전체 11,300분 · private 한도 2,000분의 5.7배
```

**한 워크플로가 전체의 76%를 먹고 있었다.** 그것도 대부분 "메시지 없음" 확인에.

게다가 **Actions cron은 부하 시 5~20분 밀린다** — 챗봇 즉답용으로 애초에 부적합하다.
즉답이 필요하면 롱폴링(`--watch`)을 상시 띄워야 하고, 워크플로는
"그게 안 떠 있을 때 질문이 묻히지 않게 하는 안전망"으로 **위치를 바꿔야 한다.**

→ 깨어 있는 시간(07~24 KST) 15분마다 → 월 2,040분. **전체 4,700분.**

## 설계 판단

**P11 대기 워크플로에 스케줄을 걸지 않았다.**
걸어두면 매일 빨간 X가 쌓이고, **빨간 X가 일상이 되면 진짜 고장을 못 알아본다.**
반대로 "성공했는데 아무것도 안 하는" 잡으로 만들면 더 나쁘다 —
돌고 있다고 착각한 채 데이터가 안 쌓인다.
→ `workflow_dispatch`만 두고, 모듈이 없으면 `::error::`로 **명시적으로 실패**한다.

**KIS 시크릿은 `universe_daily`에만 준다.** KIS를 부르는 건 `price_run` 하나뿐이다.
전 워크플로에 뿌리면 노출면만 넓어진다 — 테스트가 이를 강제한다.

**KIS 토큰 캐시는 `actions/cache`로 충분하다.** 트랩이 경고한 "매 실행 재발급"은
KIS를 쓰는 워크플로가 하루 1회뿐이라 한도에 안 걸린다.
다만 수동 재실행이 잦으면 발급 제한(분당 1회)에 걸릴 수 있어 캐시를 뒀다.

**잡 안 sleep 금지를 테스트로 강제했다**(`test_no_sleep_loop`).
sleep도 과금되므로 짧은 잡을 여러 번 띄우는 편이 싸다(PRD §10.1).
