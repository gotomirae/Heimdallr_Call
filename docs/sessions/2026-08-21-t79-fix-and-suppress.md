## 1. T79 — 플래시 알림이 스케줄에서 영영 skipped

```yaml
if: steps.season.outputs.run == 'true' && inputs.notify != false   # ← 버그
```

`schedule` 이벤트에는 `inputs`가 **아예 없다.** `inputs.notify`는 null인데
GitHub 표현식은 타입이 다르면 **숫자로 캐스팅**한다 — null도 0, false도 0이라
`null != false`가 **false**다. cron 경로에서 이 스텝은 영영 skipped였다.

### 실증 (기록을 믿지 않고 실제 실행 이력을 팠다)

시즌 게이트를 통과한 최근 실행 **7건 전부**:

```
32473220005  스크리닝=success  ⚡ 즉시 알림=skipped
32460131175  스크리닝=success  ⚡ 즉시 알림=skipped
32447879352  스크리닝=success  ⚡ 즉시 알림=skipped
32439718272  스크리닝=success  ⚡ 즉시 알림=skipped
32359618646  스크리닝=success  ⚡ 즉시 알림=skipped
32345395258  스크리닝=success  ⚡ 즉시 알림=skipped
32332750943  스크리닝=success  ⚡ 즉시 알림=skipped
```

**잡은 매번 `success`로 찍혔다.** `skipped`가 UI에서 초록색이라 잡 단위로는 안 보인다.

### 고친 방식

분기를 **셸로** 옮겼다(T55에서 `telegram_listen`에 쓴 idiom 그대로).
끄더라도 드라이런은 돌려 **"대상이 없었는지 스텝이 안 돌았는지"**를 구분한다.

### 재발 방지를 클래스 전체로 올렸다

T55 때는 `telegram_listen` 한 곳만 고치고 **개별 테스트**를 달았는데,
같은 실수가 다른 파일에서 그대로 다시 났다. 그래서 검사를 일반화했다:

> `schedule`이 붙은 워크플로의 `if:`(잡 수준·스텝 수준 모두)가 `inputs`를 보면 실패.

전수 확인 결과 `disclosure_poll.yml:101`이 **유일하게 남은** 위반이었다 —
나머지는 전부 셸 블록 안이라 이미 안전했다.

검사기 자체를 `git show HEAD:` 로 꺼낸 **수정 전 원본에 먹여 검증**했다(T54):
수정 전 1건 적발 · 수정 후 0건 · 스텝 8개를 실제로 스캔(0건을 조용히 검사한 게 아님).

## 2. 드러난 backlog — 78종목이 한 번도 안 나갔다

```
발송 대상(★/○) 78종목 · 상한 15 · 중복 건너뜀 0
  2026.2Q: 44
  2026.1Q: 34   ← 44%
```

**중복 건너뜀 0** = 전부 한 번도 발송된 적 없음.
비시즌 cron 하루 4회 × 15건이라 그냥 켜면 **약 1.3일 만에 78건 전부** 나간다.

1Q가 34건이나 상위에 있는 이유: **603종목의 2Q 재무가 미수집**이라
그 종목들의 "최신 분기"가 여전히 1Q다. 알림 품질 문제가 **수집 누락에서
조용히 흘러나온다** — 하나머티리얼즈·한선엔지니어링·와이지-원·GST 전부 1Q였다.

## 3. 사용자 결정 — 알림 생략, 대시보드에만

> "2026년 2Q 실적에 대해서는 이미 발표되었으므로 텔레그램으로 알림은 생략하고
> 대시보드에만 작성해줘"

backlog 전체(1Q 34 + 2Q 44)가 이미 발표된 과거분이라 함께 억제했다.

`python -m src.notify.batch --suppress [--save]` 추가.
`--save`가 DB 쓰기 플래그인 것은 수집기(`--save`)와 같은 관례를 따른 것이다
(`--send`는 텔레그램 쓰기, `--save`는 DB 쓰기로 갈린다).

### ★ T80 — 억제가 화면을 거짓말하게 만들 뻔했다

억제는 `notifications`에 미리 행을 넣어 `already_sent`가 막게 하는 방식인데,
**그 표는 `/settings`의 "발송 이력"이기도 하다.** 실제 발송과 똑같이 넣으면
화면이 **보내지도 않은 77건을 발송으로 센다** — 에러도 경고도 없다.

→ `payload.suppressed=true` + 사유를 남기고 화면이 갈라서 센다.

### 실측 결과

```
억제 기록 77 · 이미 이력 있음 1 · 실패 0
```

1건 스킵은 **042700(2026-08-17 실발송분)** — 진짜 보낸 기록을 덮지 않았다.

억제 후 재확인:

```
python -m src.notify.batch --flash
  → 발송 대상 78종목 · 상한 15 · 발송 0 · 중복 건너뜀 15   ← 전부 차단
```

`notifications` 84행 = 실제 발송 7(daily 5 · flash 2) + 억제 77(flash).

화면 실렌더 확인:

```
발송 이력   flash 2건 · daily 5건        ← 실제 발송분만
발송 억제   flash 77건 · 사유 표시
```

대시보드에는 그대로 나온다(저스템·하나머티리얼즈·롯데정밀화학 노출 확인).

## 막힌 것 / 미완

1. **`--suppress`는 워크플로에 넣지 않았다.** 수동 전용이 맞다 —
   자동으로 돌면 **신규 발표까지 조용히 억제**해 알림이 영영 안 나간다.
   이 도구의 위험은 정확히 그 방향이다.
2. **일일 요약(`daily_digest`)은 그대로 나간다.** 억제는 즉시 알림(`flash`)만
   막는다. 요약에는 같은 종목들이 계속 실린다 — 사용자가 멈춰 달라고 하지 않았다.
3. **2Q 재무 603종목 미수집은 그대로다.** backfill을 돌리면 1Q로 잡힌 34종목의
   순위가 바뀐다. 무료 구간(`backfill → enrich → screener --save`)이라 예산과 무관하다.
