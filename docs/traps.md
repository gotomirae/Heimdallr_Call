## T1. DART 정기보고서 누적치 — **이 프로젝트의 급소** `[설계]`

DART 정기보고서는 보고서마다 누적 기준이 다르다.

| 보고서 | `reprt_code` | `thstrm_amount` 의미 | 분기 단독값 계산 |
|---|---|---|---|
| 1분기보고서 | 11013 | 3개월 단독 | 그대로 |
| **반기보고서** | 11012 | **6개월 누적** | **Q2 = 반기 − Q1** |
| 3분기보고서 | 11014 | 3개월 단독 (+ 9개월 누적도 제공) | 그대로 |
| **사업보고서** | 11011 | **12개월 누적** | **Q4 = 연간 − 3Q누적** |

- `thstrm_amount`(당기)와 `thstrm_add_amount`(당기누적)를 **반드시 구분**하라.
- 여기를 틀리면 **Q2/Q4의 YoY가 통째로 왜곡되는데 에러는 나지 않는다.**
- Q1이 없으면 Q2를 계산할 수 없다 → `None` 반환. 0으로 채우지 마라.
- → `src/finance/quarterize.py`로 분리하고 **테스트를 먼저 쓸 것.**
  `tests/test_quarterize.py`가 이 프로젝트에서 가장 중요한 테스트다.

**⚠️ 갱신 `[HD 2026-08-13 실측 — 위 표의 "반기 = 6개월 누적"은 이 엔드포인트에서 사실이 아니다]`**

`fnlttMultiAcnt.json`을 삼성전자(CFS)·리노공업(OFS)·에스티아이(CFS) 3사로 교차 확인한 결과:

| 보고서 | `thstrm_amount` | `thstrm_add_amount` |
|---|---|---|
| 1분기 11013 | 3개월 단독 | 3개월 누적(같은 값) |
| **반기 11012** | **3개월 단독(Q2)** | **6개월 누적** |
| 3분기 11014 | 3개월 단독(Q3) | 9개월 누적 |
| **사업 11011** | **12개월 연간** | **None (없음)** |

리노공업 2025 반기: `thstrm=112,522,064,123` / `add=190,932,307,676`,
1Q 누적 78,410,243,553 → `190,932,307,676 − 78,410,243,553 = 112,522,064,123` = `thstrm`.

**그래서 `thstrm_amount`를 분기값으로 그냥 쓰면 이 엔드포인트에서는 우연히 맞는다.**
그러나 회사·계정에 따라 다를 수 있으므로 신뢰의 근거로 삼지 않는다.
→ 분해는 **항상 누적(add_amount)의 차분**으로 하고, `thstrm_amount`는
   **교차검증에만** 쓴다(어긋나면 `standalone_mismatch`에 남겨 화면에 드러낸다).
→ 반기·3분기에 누적이 없으면 3개월인지 6개월인지 알 수 없다. **추측하지 말고 판정 불가**.

## T2. 연결(CFS) / 별도(OFS) 혼용 `[설계]`

종목별로 하나를 고정하고 `fs_div`에 기록한다. **분기마다 기준이 바뀌면 성장률이 조작된 것처럼 보인다.**

## T3. 재작성(restated) 전년동기 `[설계]`

분할·합병·중단영업·회계기준 변경 시 전년동기가 재작성된다.
**공시에 실린 전년동기 값을 우선**하고, DB 저장값과 다르면 `restated=true`로 화면에 밝힌다.
조용히 예전 값을 쓰면 성장률이 실제와 달라진다.

## T4. 잠정 ≠ 확정 `[설계]`

잠정실적 공정공시 수치와 45일 뒤 확정치가 다를 수 있다.
`is_estimate` 플래그 필수, `delta_from_preliminary`에 변동 기록.
**차이 자체가 유용한 신호다** — 확정치가 잠정보다 나빠졌다면 경고다.

## T5. KIND 상장법인목록은 `html.parser`로 파싱 `[HC 2026-08-09 실측]`

`lxml`은 KOSDAQ 목록(823KB, 1,839행)에서 **1,282행에서 멈추고 예외도 경고도 내지 않는다.**
코스닥 상장사 557곳(30%)이 유니버스에서 사라지지만 아무 에러가 없어 알아채기 어렵다.

- 이 소스에만 `"html.parser"`를 쓴다. 다른 collector는 `lxml`이 정상이다.
- 원문 `<tr>` 개수와 파싱 행 수를 대조해 유실을 감지하고 **즉시 실패**시킨다.
- 회귀 방지: `tests/test_universe.py`가 코스닥 1,700개 이상을 강제한다.

## T6. KIND 응답의 종목코드 중복 `[HC 2026-08-09 실측 36건]`

같은 종목코드가 두 번 실려 오는 행이 있다(시알홀딩스 000480, 조선내화 462520 등이
완전히 동일한 내용으로 중복). code 기준 중복 제거를 안 하면 `krx_universe` PK 제약(23505)에
걸려 **캐시 저장이 통째로 실패**하고 매번 라이브 수집으로 되돌아간다
— 경고만 찍히고 분석은 계속돼 눈에 잘 안 띈다.

**⚠️ 갱신 `[HD 2026-08-13 실측 — 위 문장의 후반부는 틀렸다]`**

신규 상장 건에 `0126Z0`처럼 영문이 섞인 6자리 코드가 배정되는 것은 맞다.
그러나 **"시세 API에도 없다"는 전제는 사실이 아니다.** 실측 결과:

- 네이버 시총 API가 `itemCode='0126Z0'`으로 정상 제공한다(시총 9.98조).
- DART `corpCode.xml`에 영숫자 종목코드가 **56건** 있고,
  `company.json?corp_code=01965324` 조회도 정상이다(삼성에피스홀딩스).

이 코드를 버리면 **시총 1,000억 이상 실체 기업 12곳이 조용히 사라진다**
— 삼성에피스홀딩스 9.98조, 에임드바이오 1.75조 포함. 유니버스가 1,326 → 1,313으로
줄지만 아무 에러도 나지 않는다. KRX 종목코드 고갈로 신규 상장에는 계속 영숫자 코드가
배정되므로 시간이 갈수록 손실이 커진다.

→ 유효성 검사는 `code.isdigit()`이 아니라 **`len(code) == 6 and code.isalnum()`**.
   `krx_universe.code`가 TEXT라 저장에도 문제가 없다.
   회귀 방지: `tests/test_universe.py::test_alphanumeric_codes_are_kept`

## T7. PostgREST max-rows 1,000 `[HC 2026-08-09 실측]`

`.limit(5000)`을 줘도 **1,000행만 돌아온다**(저장 1,297행 → 조회 1,000행).
시총 내림차순으로 읽던 유니버스에서 잘려나간 건 하위 소형주 297개인데,
**이 시스템이 발굴하려는 대상이 정확히 그 구간**이라 에러 없이 품질만 나빠졌다.
1,000행을 넘길 수 있는 테이블은 반드시 `range()` 페이징.

## T8. 네이버 시총 페이징은 엄격한 내림차순이 아니다 `[HC 2026-08-09 실측]`

시총이 같은 억원대인 종목들 사이에서 순서가 흔들리는 지점이 3곳 발견됐다(915억/132억/107억 부근).
"하한 미만을 처음 본 순간"이 아니라 **그 페이지의 마지막 항목까지 하한 미만일 때**만 멈춰
최소 한 페이지 분량의 여유를 남긴다.

## T9. 시크릿에 개행이 섞인다 `[HC 2026-08-04 — 6일간 조용한 실패]`

값에 개행이 섞여 `httpcore.LocalProtocolError: Illegal header value b'***\n'`가 나고,
anthropic SDK가 그걸 `APIConnectionError("Connection error.")`로 감싸는 바람에
**모든 LLM 호출이 6일간 조용히 실패**했다.

`os.environ`을 직접 읽지 말고 반드시 `src/utils/env.py`의 `require_env`/`optional_env`
(내부에서 `.strip()`). 참고 프로젝트는 시크릿 오염이 반복돼 왔다
(`SUPABASE_URL`에 `/rest/v1`이 붙는 사고 3회 + 개행 1회).

## T10. 미선언 의존성 `[HC — 3회 재발]`

새 서드파티 임포트를 `pyproject.toml`에 선언하지 않으면, 로컬 venv에 수동 설치돼 있어
**로컬 테스트는 전부 통과하고 GitHub Actions의 깨끗한 `pip install -e .` 환경에서만 죽는다.**

`lxml`은 더 악질이었다 — 임포트 시점이 아니라 **실제로 파싱을 수행하는 순간**에만
`bs4.exceptions.FeatureNotFound`로 죽어서, 파싱할 대상이 없는 대다수 실행은 초록불로 끝났다.

검증: `python -m venv /tmp/x && /tmp/x/bin/pip install -e .` 후 실제 경로 1회 실행.
(`pip show <pkg>`의 `Required-by`가 비어 있으면 수동 설치된 것 = 선언 누락 신호)

## T11. 단위를 못 읽으면 추측해서 곱하지 말 것 `[HC 2026-08-06]`

잠정실적 공시 원문 표는 원/백만원/억원이 섞인다.
단위 파싱 실패 시 **그 항목만 건너뛰고** 그 사실을 화면에 밝힌다. 회사·분기마다 다르므로
종목별 고정 가정도 금물이다.

(DART API는 원 단위 정수라 이 문제가 없다 — L2' 규칙 파서·Haiku 폴백에만 해당)

## T12. 부호가 바뀌는 구간의 성장률 `[설계]`

적자→흑자, 흑자→적자에서 % 계산은 무의미하다.
분모가 0 또는 음수면 `None`을 반환하고 `op_status_label`에
`'흑전' | '적전' | '적자축소' | '적자확대'` 중 하나를 넣는다.

## T13. 텔레그램 웹훅 `[설계]`

**`setWebhook` 호출 금지.** 텔레그램은 봇당 웹훅 1개만 허용하고,
새로 등록하면 이전 것이 **에러 없이 덮어써진다.**
HermesCall 대시보드가 점유 중이라 등록 시 HermesCall 봇 명령어가 조용히 죽는다.
Heimdallr는 `sendMessage` 발송 전용.

발송 rate limit도 봇 토큰 공유로 함께 쓴다 — 연속 발송 1초 간격,
429의 `retry_after` 존중 백오프 3회.

## T14. 4Q의 특수성 `[설계]`

한국 기업 4Q는 일회성 비용(재고평가손·성과급·손상차손)이 집중되어 OPM이 구조적으로 낮고,
사업보고서 차감으로 산출되므로 **잔차에 모든 회계 조정이 몰린다.**
4Q 스코어에는 신뢰도 플래그를 붙이고, 4Q QoQ 관련 판정은 하지 않는다.

## T15. KIS API — 토큰 재발급 제한과 초당 유량 `[설계]`

- **접근토큰을 매 실행마다 새로 받으면 발급 자체가 막힌다.**
  `.cache/kis_token.json`에 만료시각과 함께 캐시하고 만료 전까지 재사용할 것.
  GitHub Actions 러너는 매번 초기화되므로 `actions/cache` 또는 Supabase에 보존해야 한다.
- **유량 실전계좌 초당 20건.** 1,300종목 순회 시 토큰버킷 스로틀러(안전 마진 18/초)가
  없으면 중간에 `EGW00201`로 죽는다.
- **응답 필드명을 추정으로 박지 말 것.** 실제 호출 1회로 확정한 뒤 코드에 넣는다.
- **주문 API 호출 금지.** 시세 조회 화이트리스트 밖은 클라이언트 내부에서 차단한다.

## T16. `.env`의 SUPABASE 값이 HermesCall 것일 수 있다 `[설계]`

프로젝트 폴더의 `.env.txt`에 이미 Supabase 값이 들어 있으나,
**Heimdallr는 신규 Supabase 프로젝트를 쓴다**(ADR 8).
값을 그대로 쓰면 HermesCall DB에 Heimdallr 테이블이 생성되어 분리 이유가 통째로 무너진다.
P0에서 `SUPABASE_URL`의 프로젝트 ref(`https://<ref>.supabase.co`)가 HermesCall과 다른지
**눈으로 대조**할 것.

**키 형식이 바뀌었다(2026 기준).** Supabase는 legacy JWT 키(`anon` / `service_role`)를
**2026년 말 deprecate** 예정이며, 신규 프로젝트는 `sb_publishable_...` / `sb_secret_...`를 쓴다.
- `SUPABASE_SERVICE_KEY` ← **secret 키**(`sb_secret_...`) — 서버사이드 전용, RLS 우회
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` ← **publishable 키**(`sb_publishable_...`) — 대시보드 읽기 전용
- 환경변수 **이름은 그대로 두고 값만 신규 형식**을 넣는다(코드 변경 불필요).
- publishable 키는 `anon`과 동일한 저권한이라 `schema.sql`의 `TO anon` RLS 정책이 그대로 동작한다.
  다만 **P0 검증 때 실제로 anon 조회가 되는지 1회 확인할 것** — 추측하지 말 것.
- ⚠️ `sb_secret_...`를 대시보드 프론트엔드 환경변수(`NEXT_PUBLIC_*`)에 절대 넣지 마라.
  RLS를 우회하므로 노출 시 전체 데이터가 열린다.

## T17. 컨센서스는 발표되면 사라진다 `[설계]`

FnGuide/네이버의 분기 컨센서스는 `(E)` 표기로 나오는데 실적이 발표되면 실적치로 덮여 사라진다.
**발표 후에 조회하면 이미 늦다.** 시즌 직전부터 주 1회 스냅샷해 `consensus_snapshots`에
쌓아야 F1(서프라이즈)이 성립한다.

## T18. 대시보드 — 부분 채움 JSONB와 미적용 컬럼 `[HC 2026-08-06 실제 발생]`

1. `analyses.payload`는 부분적으로만 채워질 수 있다. `payload && payload.scenarios.bull`처럼
   상위 객체만 확인하고 하위 필드를 읽으면 **페이지 전체가 500**이 난다. 필드 단위로 확인하라.
2. 새 컬럼을 추가하면 SQL Editor 적용 전까지 공백이 생기는데, 그 사이
   쓰기는 **PGRST204**로, 조회는 **42703**으로 각각 파이프라인과 페이지 전체를 죽인다.
   누락 컬럼을 감지해 제외하고 재조회하는 루프 패턴을 쓸 것
   (PostgREST는 누락 컬럼을 한 번에 하나씩만 알려주므로 루프가 필요하다).

## T19. Anthropic 가격에 날짜 기준 전환 로직 금지 `[2026-08-13 확인]`

HermesCall은 2026-09-01부터 Sonnet 5 단가를 $3/$15로 전환하도록 짜여 있으나,
Anthropic 공식 가격 페이지 확인 결과 **$2/$10이 정가로 확정됐고 인상은 시행되지 않는다.**
그대로 두면 비용이 50% 과대 계상되어 월 실링에 조기 도달한다.

## T20. GitHub Actions에서 `sleep` 루프 금지 `[설계]`

`sleep`도 과금된다. 긴 잡 하나보다 **짧은 잡을 여러 번** 띄우는 편이 싸다.

발표 후 D+20 초과수익을 재는데, 시즌이 막 끝나면 **거래일이 모자라 대부분 측정이 안 된다.**

실측: 2026.2Q 459건 중 D+20 측정 가능 **2건**(발표일 20260715~20260813, 오늘 20260816).

여기서 미측정을 0%로 채우면:
- 평균·중앙값이 0 쪽으로 끌려간다
- 등급별 차이가 사라져 **"스코어가 아무 효과 없다"**는 결론이 나온다
- 실제로는 그냥 **아직 시간이 안 지난 것**이다

수익률 0%("안 움직였다")와 "20거래일이 안 지났다"는 완전히 다른 상태다.

→ `None` + 사유(`거래일 부족(아직 이르다)` / `거래정지 또는 상장폐지`).
  화면과 리포트에 **측정 건수를 값과 함께** 낸다(`+4.99(9)` — 중앙값과 n).
  n=1짜리 중앙값을 신호로 읽는 사고를 막는다.

**같이 걸리는 것 셋:**

**① 거래일로 세야 한다 — 캘린더 일수가 아니다.**
휴장일이 섞이면 20일이 14거래일이 되고 종목마다 다른 날을 비교하게 된다.
**숫자는 그럴듯하게 나온다.**

**② 발표일이 휴장일이면 다음 거래일이 기준이다.**
장 마감 후·주말 공시가 실제로 많다. 그날이 시장이 처음 반응할 수 있는 날이다.

**③ 발표일은 그 분기 공시 중 가장 이른 것.**
정정·상세 공시를 발표일로 잡으면 시장이 이미 반응한 뒤부터 재기 시작해
**초과수익이 통째로 사라진다.**

**그리고 D+1로 판단하면 안 된다.** 실측에서 ★ 그룹이 D+1 −3.31%p로 가장 낮은데
D+5에서는 +4.99%p로 가장 높다. **미반영 종목은 반응이 늦게 오는 게 설계상 정상이다**
(그래서 PRI가 낮은 것이다). 시점을 안 밝히고 IC를 보여주면 정반대로 읽힌다.

```bash
git grep -c -F -- "$val" --cached | wc -l     # ← 항상 0
```


**교훈: 검사기는 반드시 "반드시 걸려야 하는 입력"으로 자기 자신을 먼저 검증하라.**

## T55. GitHub 삼항 `inputs.x && A || B`는 **양방향으로** 조용히 틀린다 `[HD 2026-08-17 실측]`

`telegram_listen`이 이렇게 돼 있었다:

```yaml
run: python -m src.notify.listen --once ${{ inputs.analyze && '--analyze' || '' }}
```

**틀림 ①: `schedule`에는 `inputs`가 존재하지 않는다.**
항상 빈 문자열이 되어 **cron 경로에서 LLM이 영영 호출되지 않았다.**
로그는 매번 `LLM 분석 OFF`를 정직하게 찍고 있었지만, 워크플로는 성공(초록)이고
텔레그램 회신도 정상적으로 나가서 — **해석 문단만 빠진 채** — 아무도 눈치채지 못했다.
`ANTHROPIC_API_KEY`는 시크릿으로 등록돼 있는데 **한 번도 안 쓰였다.**

**틀림 ②: 반대 방향도 안 된다.** GitHub 표현식에서 `false`는 falsy라
`inputs.x && A || B`는 x가 **false일 때도 B**를 준다.
즉 기본값만 뒤집으면 이번엔 "수동으로 끄기"가 에러 없이 무시된다.
JS의 같은 관용구를 그대로 옮기면 이 함정을 반드시 밟는다.

→ 분기를 **셸로** 옮겼다. 값 비교라 fall-through가 없다:

```yaml
env:
  ANALYZE_INPUT: ${{ inputs.analyze }}   # schedule이면 빈 문자열
run: |
  if [ "$ANALYZE_INPUT" = "false" ]; then
    python -m src.notify.listen --once
  else
    python -m src.notify.listen --once --analyze
  fi
```

실측 검증(두 경로를 **둘 다** 돌렸다 — 한쪽만 보면 ②를 못 잡는다):

```
기본 디스패치        → 허용 chat: [***] · LLM 분석 ON
-f analyze=false    → LLM 분석 OFF — 수동 실행에서 명시적으로 껐다
```

**곁다리로 드러난 것:** `--analyze`를 켜자 timeout 5분이 부족해졌다.
`confirm()`이 **배치를 다 처리한 뒤에야** offset을 확정하므로(`listen.py`),
BATCH 20건 × 분석 30초에서 죽으면 확정이 안 되고 **같은 20건이 계속 재배달된다**
→ 매번 같은 자리에서 죽는 빨간 X 루프가 되고 질문은 영영 답을 못 받는다. → 12분으로.

**교훈: 플래그를 켜는 변경은 켠 경로와 끈 경로를 둘 다 실행해 확인하라.**
켠 쪽만 보면 "동작한다"로 보이는데, 정작 되돌릴 수단이 죽어 있다.

## T56. **배포 URL은 프로젝트 이름에서 추론하지 말고 실제로 열어봐라** `[HD 2026-08-17 실측]`

Vercel 프로젝트명이 `heinmdallr`라는 말을 듣고 기본 URL을 `https://heinmdallr.vercel.app`으로
바꿨다(코드 상수 + `.env.example` + GitHub 저장소 변수 3곳). 그럴듯했다.

```
https://heinmdallr.vercel.app/       → HTTP 404
https://heimdallr-call.vercel.app/   → HTTP 200
```

Vercel URL은 프로젝트 이름과 **항상 같지 않다** — 이름 충돌 시 접미사가 붙고,
저장소명·팀명에서 파생되기도 하며, 나중에 바꾼 이름이 도메인에 반영되지 않기도 한다.

**무엇이 조용히 틀리는가:** 이 값이 틀려도 아무것도 실패하지 않는다.
워크플로는 초록, 텔레그램 메시지는 멀쩡, 링크는 정상 형태.
**누가 폰에서 링크를 눌러보기 전까지** 전 메시지의 링크가 죽어 있다.
게다가 이 프로젝트는 링크를 fallback 상수 + 저장소 변수 **두 층**으로 두는데,
둘 다 같은 오답으로 맞춰 놓으면 이중화가 아무 의미가 없다.

→ `curl -o /dev/null -w "%{http_code}"`로 **양쪽을 다 찍어** 확정한 뒤 되돌렸다.
→ `test_dashboard_url_default_matches_env_example`로 두 선언이 어긋나는 것은 막았다
   (실제 도메인과의 일치는 테스트가 검증할 수 없다 — 네트워크가 필요하다).

**함께 확인한 배포 점검법** (로그인한 브라우저로는 못 잡는 것들):

```bash
curl -s -o /dev/null -w "%{http_code}" https://<url>/     # 401이면 Deployment Protection
curl -s https://<url>/api/cost                            # available:false면 서버 키 누락
```

배포자 브라우저는 Vercel에 로그인돼 있어 보호가 켜져 있어도 **그냥 열린다.**
`available:false`와 `spentUsd:0`도 화면에서는 둘 다 "0"처럼 보인다(T51).
**미인증 요청으로 확인하라 — 그게 폰과 같은 조건이다.**

## T64. `overflow-x-auto`가 **머리글 고정을 조용히 무력화한다** `[HD 2026-08-17 실측]`

표 머리글을 고정하려고 이렇게 썼다:

```tsx
<div className="overflow-x-auto rounded-lg border border-slate-800">
  <table>
    <thead className="sticky top-0 z-10 bg-slate-900">
```

**아무것도 실패하지 않는다.** 클래스는 그대로 붙어 있고, 빌드·tsc 통과, 콘솔 경고도 없다.
코드만 보면 완벽하게 맞다. 그런데 **스크롤하면 머리글이 그냥 같이 올라간다.**

원인은 CSS 사양이다. 한 축이 `visible`이 아니면 **다른 축의 `visible`은 `auto`로 계산된다** —
즉 `overflow-x: auto`를 주는 순간 이 div는 **세로축도 스크롤 컨테이너**가 된다.
그런데 높이 제한이 없어 실제로는 세로로 스크롤되지 않고 **페이지가** 스크롤된다.

`position: sticky`는 **가장 가까운 스크롤포트**를 기준으로 붙는다. 그 스크롤포트가 이
div인데 이 div는 세로로 안 움직이므로, thead는 영영 "붙는" 상태가 되지 않고
페이지와 함께 밀려 올라간다.

→ 높이를 제한해 그 div를 **실제 세로 스크롤 영역**으로 만든다.

```tsx
<div className="max-h-[70vh] overflow-auto …">
  <thead className="sticky top-0 z-20 bg-slate-900 shadow-[0_1px_0_0_rgba(148,163,184,0.35)]">
```

- `bg-*`가 **반드시** 있어야 한다. 투명하면 본문이 머리글 뒤로 비쳐 지나간다.
- `z-index`는 본문 셀보다 높아야 한다(여기선 20).
- 같은 패턴을 쓰는 표가 셋 있었다(발굴목록·분기히스토리·스크리너) — **한 곳만 고치면
  나머지는 계속 조용히 안 된다.** `overflow-x-auto`를 grep으로 전수 확인했다.

**교훈:** 눈으로 스크롤해 보기 전까지 이 종류는 절대 드러나지 않는다.
"클래스를 넣었으니 됐다"가 검증이 아니다.

## T65. 차트 색을 **설명 글에 손으로 적으면** 조용히 어긋난다 `[HD 2026-08-17]`

## T66. 회고 분석에서 **1위가 음수인데 "가장 컸다"고 말한다** `[HD 2026-08-17 실측]`

결과 추적 화면에 "언제 샀어야 했나"를 넣고 시점별 중앙 초과수익 중 최대를 골랐다.
그 문장이 이렇게 나갔다:

> 초과수익이 가장 컸던 구간은 **발표 후 5일**이다 (중앙값 **−0.73%p**).
> → 발표를 확인하고 들어가도 늦지 않았다. 확인 후 진입이 위험 대비 유리했다.

**중앙값이 음수다.** 비교상 1위였을 뿐 지수를 못 이겼는데, 화면은 강세 전략을
권하고 있었다. 코드에는 버그가 없다 — `Math.max`는 정확히 최댓값을 골랐다.
**부호를 안 본 것이 버그다.**

이 형태가 위험한 이유: 숫자와 문장이 같은 화면에 있는데도 **문장이 숫자를 배반한다.**
읽는 사람은 문장을 먼저 믿는다. 그리고 이건 투자 조언이라 대가가 크다.

→ 1위의 부호를 반드시 본다.

```ts
const positive = best.cell.median > 0;
headline = positive
  ? `초과수익이 가장 컸던 구간은 ${label}이다 (${fmt(best.median)}).`
  : `어느 구간에서도 지수를 이기지 못했다. 그중 가장 나았던 구간이 ${label}인데
     그마저 ${fmt(best.median)}다.`;
action = positive ? "…확인 후 진입이 유리했다." : "게이트 통과만으로 사는 전략은 통하지 않았다.";
```

**교훈:** 집계에서 뽑은 문장은 **극값의 부호·표본 수·방향**을 전부 확인해야 한다.
"최대"는 "좋다"가 아니다.

| 8~23건 | 참고 | 방향만 |

**대조에서 어긋나면 어느 쪽이 틀렸는지부터 확인하라.**

```
✓ 롯데정밀화학 $0.0351 (캐시 미스)   ← 첫 건만
✓ 엠플러스     $0.0248 (캐시 히트)
✓ 미래반도체   $0.0303 (캐시 히트)
```

## T72. **발송 기준과 분석 기준이 갈라져 있었다** `[HD 2026-08-17 실측]`

텔레그램 알림은 **등급** 기준이다:

```python
NOTIFY_GRADES = ("★", "○")
```

그런데 LLM 배치는 **스코어** 기준으로 뽑았다:

```python
if float(r["score_flash"]) >= SCORE_HIGH:   # 75
```

**등급은 스코어와 반영도의 교차 판정이다.** 스코어가 조금 낮아도 반영도가 매우
낮으면 ○가 된다 — 이 시스템이 찾는 바로 그 구간이다. 두 기준이 갈라져 있으니
그 종목들이 사이로 빠졌다.

실측: **발송 대상 70종목 중 22종목이 해석 없이 알림만 나가고 있었다.**

```
○ KBI동양철관   스코어 74.9  반영도  3.4   ← 0.1점 차이
○ 롯데케미칼     스코어 68.7  반영도  2.7   ← 반영도 2.7
○ GKL         스코어 69.3  반영도  1.8   ← 반영도 1.8
```

**반영도가 낮은 종목이 특히 많이 빠졌다.** 하필 가장 중요한 종목들이다.

**무엇이 조용히 틀리는가:** 배치는 "66종목 분석 완료"로 성공을 보고하고,
알림도 정상 발송된다. 어느 쪽도 실패하지 않는다. 알림을 하나씩 열어 보고
"이 종목은 왜 해석이 없지?"를 묻기 전까지 드러나지 않는다.

→ 선정 조건에 **발송 등급을 무조건 포함**한다.

```python
r["grade"] in NOTIFY_GRADES
or (score is not None and score >= min_score)
```

**교훈:** "누구에게 알리나"와 "누구를 분석하나"처럼 **같은 대상을 가리켜야 하는
두 기준**은 반드시 한쪽이 다른 쪽을 포함하도록 코드로 묶어라.
숫자 하한과 등급을 각자 두면 언젠가 갈라진다.

`tests/test_analysis_batch.py`가 **어떤 하한을 줘도** 발송 등급이 빠지지 않는지 검사한다.

## T73. LLM 배치는 **한 워크플로 안에서 끝나지 않는다** `[HD 2026-08-17 실측]`

게이트 통과 238종목 전부를 분석하기로 했는데(B안) 실측이 이랬다:

```
호출당 소요   36~56초  (출력 2,400~2,800토큰 생성이 느리다)

disclosure_poll timeout-minutes: 15
```

그냥 얹으면 **매번 15분에 강제 종료**된다. 그러면 진행 상황이 로그에 안 남아

★ `concurrency`에 `cancel-in-progress: false`를 준다. 도는 중에 새로 띄우면

## T74. **"재무를 수집했는가"로 "발표했는가"를 판정했다** `[HD 2026-08-17 실측]`

시즌 화면이 2분기 실적을 이미 발표한 종목을 **미발표로 분류**했다.
같은 대시보드의 '최근 공시' 목록에는 그 반기보고서 링크가 멀쩡히 걸려 있었다.

원인은 판정 기준이었다:

```ts
const reported = new Set(
  usable.filter((f) => qIndex(f) === latest && f.revenue != null).map((f) => f.code)
);   // ← quarterly_fundamentals만 본다
```

`disclosures`를 **불러오기는 했는데 캘린더 막대에만 썼다.** 발표 여부 판정에는
쓰지 않았다. 그래서 "공시는 났지만 재무 수집이 안 된" 종목이 전부 미발표가 됐다.

실측 규모:

```
대상 1,112종목
  재무 수집 완료      482
  공시는 났는데 재무 없음  609   ← 전부 '미발표'로 표시됐다
  진짜 미발표          21
진행률  43.4%  →  실제 98.1%
```

빠진 종목이 하필 대형주였다 — 대한항공(9.6조)·레인보우로보틱스·삼양식품·
이수페타시스·유한양행·리노공업.

**무엇이 조용히 틀리는가:** 화면은 정상이고 숫자도 그럴듯하다.
"아직 발표 안 한 종목이 630개"는 시즌 중이라면 충분히 있을 수 있는 값이다.
**공시 목록과 나란히 놓고 비교하기 전까지** 드러나지 않는다.

→ 세 상태를 **구분해서** 보여준다. 하나로 뭉치면 원인을 못 찾는다.

| 상태 | 뜻 | 조치 |
|---|---|---|
| 재무 수집 완료 | 판정 가능 | — |
| 공시만 (수집 대기) | **발표는 됐다** | 며칠 지나도 남으면 수집기 확인 |
| 미발표 | 공시도 재무도 없다 | 마감일 지나면 공시 수집 확인 |

진행률은 **공시 기준**으로 잰다 — 재무 수집은 우리 쪽 사정이고,
"시즌이 얼마나 진행됐나"는 시장이 얼마나 발표했나로 재야 한다.

★ **`earnings_disclosures.fiscal_quarter`는 전 행이 null이다**(실측 1,558/1,558).
  수집기가 채우지 않는다. 그래서 분기를 보고서명에서 뽑는다:

```
반기보고서 (2026.06)          → 2026.2Q
[기재정정]반기보고서 (2026.06)  → 2026.2Q
사업보고서 (2025.12)          → 2025.4Q
연결재무제표기준영업(잠정)실적    → 월이 없다 → 공시일로 추정
```

**보고서명을 먼저 본다.** 공시일 추정은 분기 경계에서 틀린다 —
7월 초에 나온 1Q 정정 공시를 2Q로 읽어버린다.

## T76 ★ 텔레그램 env를 `""`로 덮어도 **실제로 발송된다** (테스트가 진짜 메시지를 보냄)

`notify_progress()`가 실패해도 배치를 세우지 않는지 검증하려고
`HEIMDALLR_TELEGRAM_BOT_TOKEN=""`·`..._CHAT_ID=""`로 monkeypatch하고
"토큰이 없으니 예외 → False"를 기대했다. **테스트가 실패했고, 그 이유는 실제 발송이 성공했기 때문이다.**
사용자 텔레그램에 `🛡️ 테스트`가 한 건 나갔다(2026-08-17).

원인 — `src/notify/telegram.py`의 폴백 사슬:

```python
dedicated = optional_env("HEIMDALLR_TELEGRAM_BOT_TOKEN")
return dedicated or require_env("TELEGRAM_BOT_TOKEN")   # ← 빈 문자열이면 여기로 떨어진다
```

`""`는 falsy라 **공유 봇 자격증명(`TELEGRAM_*`)으로 조용히 폴백**한다.
그리고 `.env.txt`에 그 값이 살아 있다. 즉 **"비활성화했다고 믿은 설정이
다른 경로로 활성 상태**가 된다 — 발송이니 되돌릴 수도 없다.

→ **발송 계열을 테스트할 때 env를 비우지 마라. 클라이언트 자체를 갈아끼워라.**

```python
import src.notify.telegram as tg
monkeypatch.setattr(tg, "TelegramClient", boom)   # 네트워크에 닿을 길을 없앤다
```

★ 같은 모양이 T51(RLS가 에러 대신 빈 배열)·T54(검사기가 fatal에도 0)와 같다:
  **"막았다고 믿은 것이 조용히 안 막혀 있다."** 차이는 여기선 결과가
  화면이 아니라 **남의 휴대폰에 남는다**는 것이다.

## T78 ★ 재시도가 짧으면 **남의 서버 딸꾹질에 우리 잡이 죽는다**

## T79 ★★★ 플래시 알림이 **스케줄에서 영영 skipped**였다 (T55가 다른 파일에서 재발)

`disclosure_poll.yml`의 마지막 스텝:

```yaml
- name: ⚡ 즉시 알림
  if: steps.season.outputs.run == 'true' && inputs.notify != false

```

**`schedule` 트리거에는 `inputs`가 없다.** GitHub 표현식은 타입이 다르면 숫자로 캐스팅하므로
`null != false` → `0 != 0` → **false**. 즉 이 스텝은 **cron에서 단 한 번도 돌지 않았다.**

실측(run 32359618646, 2026-08-20):

```
success  스크리닝
success  LLM 배치 분석 (신규 우선)
skipped  ⚡ 즉시 알림        ← 여기
```

**왜 아무도 몰랐나** — 증상이 "에러"가 아니라 "조용함"이다. 잡은 초록색이고,
로그에는 `발송 대상(★/○) 68종목`까지 멀쩡히 찍힌다. 대상을 **계산까지 해 놓고

그 2건은 수동 E2E 검증에서 나온 것이다. 비시즌이라 "발표가 없어서 조용한 것"으로
읽혔다 — **정상 동작과 고장이 똑같이 생겼다.**

★ 이 시스템의 **존재 이유가 발송**이다. 11월 `SEASON_MODE=on`이 되면 시즌 내내

→ 교훈:
- **T55를 문서에 적어 두는 것만으로는 재발을 못 막는다.** 같은 함정이 다른 파일에
  그대로 있었다. 조건 분기는 **셸 안에서** 하고, YAML `if`에는 `steps.*` 출력만 쓴다.
- **`skipped`는 초록색이다.** 잡 성공만 보면 안 되고 **스텝 결론을 봐야 한다**:
  `gh api .../jobs --jq '.jobs[].steps[] | "\(.conclusion)\t\(.name)"'`
- 부작용이 있는 스텝은 **"이번에 몇 건 보냈다"를 로그에 남겨라.** "대상 68종목"만
  찍고 끝나면 보냈는지 안 보냈는지 로그로 구분할 수 없다.

603종목의 2Q 재무가 아직 미수집이라 그 종목들의 "최신 분기"가 여전히 1Q이기
때문이다. **알림 품질 문제가 수집 누락에서 조용히 흘러나온다.**

억제는 `notifications`에 미리 행을 넣어 `already_sent`가 막게 하는 방식인데,
**여기에 함정이 있다.** 그 표는 화면의 "발송 이력"이기도 하다 —
실제 발송과 똑같이 넣으면 `/settings`가 **보내지도 않은 77건을 발송으로 센다.**
에러도 경고도 없고 화면은 멀쩡하다.

→ `payload.suppressed=true` + 사유를 남기고, 화면이 **갈라서** 센다.
  실측: 발송 이력 `flash 2 · daily 5` / 발송 억제 `flash 77`.

같은 이유로 지켜야 하는 두 가지:

- **종류(`kind`)는 실제 발송과 같아야 한다.** 다르게 넣으면 `already_sent`가
  못 잡아 **억제가 아무것도 막지 못한다** — "안 보내려고 넣었는데 그대로 나간다"가
  이 기능의 최악 실패다.
- **상한을 적용하면 안 된다.** 일부만 억제하면 나머지가 다음 실행에 그대로 나간다.
  "억제했다"는 기록만 남고 실제로는 절반이 발송된다.
- **이미 있는 이력은 덮지 않는다.** 진짜 보낸 사실이 억제 표식으로 사라진다
  (실측: 042700 1건이 2026-08-17 실발송분이라 건너뛰어졌다 — 77 기록 · 1 스킵).

**교훈: 중복 차단 표를 의도적으로 채울 때는, 그 표를 읽는 화면도 같이 고쳐라.**
한 테이블이 "기계용 자물쇠"와 "사람용 기록" 두 역할을 겸하면 둘이 조용히 어긋난다.

## T81. 발송 억제는 데이터가 갱신되면 조용히 풀린다 `[HD 2026-08-21 실측]`

억제는 `notifications`의 **(종목, 연, 분기, 종류)** 키로 막는다.
그런데 그 "분기"는 **고정값이 아니다** — 스크리너는 종목별 최신 발표 분기를
쓰므로(T36), 재무가 새로 수집되면 같은 종목의 대상 분기가 **앞으로 이동한다.**

2026-08-21 실측:

```
backfill 전  억제 78종목 = 2026.1Q 34 + 2026.2Q 44
backfill 후  대상 107종목 = 2026.1Q  3 + 2026.2Q 104
                              ↑ 60여 종목이 1Q → 2Q로 이동
```

1Q로 억제해 둔 종목이 2Q로 넘어가면 **키가 달라져 억제가 걸리지 않는다.**
`notifications`에는 그 종목의 억제 기록이 멀쩡히 남아 있으므로
"억제해 뒀다"고 믿기 딱 좋다 — 실제로는 다음 cron에서 그대로 나간다.
새로 게이트를 통과한 종목(78 → 107)도 당연히 안 막혀 있다.

→ **`screener --save` 뒤에는 반드시 억제를 다시 돌린다.**
  실측: 재실행에서 `억제 기록 60 · 이미 이력 있음 47` — 60건이 새로 막혔다.
  검증은 상한(15) 밖까지 봐야 한다. `--flash`는 상위 15건만 검사하므로
  **"발송 0"을 보고 안심하면 안 된다**:

```python
un = [r for r in notify_targets()
      if not already_sent(r['code'], r['fiscal_year'], r['fiscal_quarter'], KIND_FLASH)]
# 발송 대상 107 · 차단 안 된 건 0
```

**교훈: "이미 처리했다"를 파생 키로 기록하면, 그 키가 움직일 때 처리가 무효가 된다.**
분기·버전·해시처럼 **갱신되는 값이 키에 들어가면** 재실행 시점을 반드시 함께 설계하라.

## T82. 상한이 다섯 곳에 흩어져 있었고, 넷이 서로 달랐다 `[HD 2026-08-21 실측]`

월 실링을 $12 → $20으로 올리려다 발견했다. 같은 값이 **다섯 곳**에 있었다:

| 위치 | 당시 값 | 실제로 쓰이나 |
|---|---:|---|
| `src/config/constants.py` | **12** | ✔ 이것만 쓰인다 |

| `docs/PRD.md` 부록 상수표 | **8** | 문서 — **4일간 낡은 채였다** |
| 워크플로 주석 3곳 | 8 · 8 · 12 | 주석 |

### ① env로 조절되게 설계했는데 워크플로가 안 넘긴다

```python
MONTHLY_COST_CEILING_USD = optional_env_int("MONTHLY_COST_CEILING_USD", 12)
```

`optional_env_int`라 저장소 변수로 조절할 수 있게 만들어 놓고, 정작

그 env를 넘기지 않았다. GitHub Variable을 만들어도 **에러 없이 무시되고**
코드 기본값이 쓰인다 — "올렸는데 왜 그대로지"를 로그로는 알 수 없다.

→ 세 워크플로에 `${{ vars.MONTHLY_COST_CEILING_USD }}` 배선.
  판정 기준을 파일명이 아니라 **`ANTHROPIC_API_KEY` 보유**로 잡아
  새 워크플로가 생겨도 자동으로 검사에 걸리게 했다.

### ② ★ 첫 매치가 나머지를 가린다

PRD↔코드 대조 테스트는 **이미 있었다.** 그런데 `re.search`를 써서
**첫 매치만** 봤다. PRD는 같은 상수를 §7.3과 부록 두 곳에 적는데,
§7.3만 갱신되고 부록은 8인 채로 남았는데도 **테스트는 계속 초록불**이었다.

```
search  → '12'          ← 통과
findall → ['12', '8']   ← 실패해야 했다
```

→ `findall`로 바꿔 **전수 대조**. 실측으로 확인했다(수정 전 원본에 먹여 검증, T54).

**교훈: 문서·설정의 값을 대조할 때 `search`는 검사기를 반쯤 무력화한다.**
같은 이름이 두 번 나올 수 있으면 **`findall` + 전부 일치**로 써라.
T50("문자열 치환이 엉뚱한 곳에 걸려도 출력은 그럴듯하다")과 같은 뿌리다.

### ③ 주석에 적은 숫자는 반드시 어긋난다

세 워크플로 주석이 같은 상한을 두고 `월 $8` · `월 $8 · 일 20건` · `월 실링 $12`라고
말하고 있었다. 코드는 12였다 — **셋 다 틀렸다.** 숫자를 지우고 출처
(`src/config/constants.py`)를 가리키게 바꾸고, 주석에 상한 숫자가 박히면
실패하는 검사를 넣었다(T65와 같은 부류).

## T83. 일 상한과 월 실링을 같은 말로 알리면 사람이 틀린 행동을 한다 `[HD 2026-08-21 실측]`

실측 종목: 그린케미칼(083420) · 유비쿼스(264450) · 동국씨엠(460850).

**또 올리면 모든 호출의 상한이 올라가므로**, 올리기 전에 "이 종목들만 왜 긴가"를 먼저 봐야 한다.

**교훈: 실패한 호출의 비용을 따로 세라.** 성공 건수와 평균 단가만 보면
"3건 실패"가 비용의 13%라는 사실이 드러나지 않는다.

## T86. 복원 effect를 ref로 잠그면 저장 effect가 **같은 커밋에서** 그걸 덮어쓴다 `[HD 2026-08-22 실측]`

발굴 목록 필터를 sessionStorage에 저장해 탭을 오갈 때 유지하려 했는데,
다른 탭에 갔다 돌아오면 **매번 초기화**됐다.

```jsx
const restored = useRef(false);
useEffect(() => { setFilters(loadStored()); restored.current = true; }, []);   // 복원
useEffect(() => { if (!restored.current) return; saveStored(filters); }, [filters]);  // 저장
```

마운트 시 두 effect가 **같은 커밋에서 연달아** 돈다. 복원 effect의 `setFilters`는
아직 반영되지 않았으므로 저장 effect가 보는 `filters`는 **여전히 기본값**인데,
`restored.current`는 이미 `true`다 → **기본값을 저장해 방금 읽은 값을 지운다.**

개발 모드의 StrictMode 이중 실행이 이걸 확정타로 만든다:
지워진 저장소를 두 번째 복원 실행이 다시 읽어 기본값을 굳힌다.

**고치는 법:** `useRef`가 아니라 `useState`. state면 저장 effect가
**복원된 값과 같은 렌더**에서만 켜지므로 순서가 보장된다.

**교훈: "이미 초기화됐는가" 플래그를 ref로 두면 순서 보장이 사라진다.**
그 플래그가 다른 effect의 실행 조건이라면 **렌더에 묶인 state**여야 한다.
그리고 상태 복원은 **개발 모드에서 반드시 탭을 오가며 확인하라** — 첫 로드만 보면 통과한다.

## T87. 값의 단위와 **차이의 단위**가 다르다 (%와 %p) `[HD 2026-08-22 실측]`

내러티브 검증 표가 이렇게 나왔다:

```
매출 YoY        +123.9% → +43.1%    분석 이후 -80.8% 낮아졌다     ← 매출이 80% 줄었다는 뜻으로 읽힌다
영업이익률(OPM)  +33.9%  → +33.9%    분석 이후 -0.0%p 낮아졌다  · 미달   ← 같은 숫자인데 미달
```

두 가지가 겹쳤다.
1. **성장률의 차이는 `%`가 아니라 `%p`다.** 123.9% → 43.1%는 성장률이
   80.8%**p** 낮아진 것이지 매출이 80.8% 준 게 아니다. 같은 기호를 쓰면 문장이 거짓말을 한다.
2. **표시 자릿수보다 작은 차이로 판정이 뒤집혔다.** OPM이 소수 셋째 자리에서만
   0.001%p 낮았는데 `after >= before`가 false라 **미달**이 됐다.
   화면에는 **같은 숫자 두 개와 '미달'이 나란히** 떠서 읽는 사람이 자기 눈을 의심하게 된다.

→ 값은 `%`, 차이는 `%p`로 분리하고 `EPSILON_PP = 0.05`(표시 해상도 0.1보다 작게)를 뒀다.

**교훈: 비교 판정에는 표시 자릿수와 짝이 맞는 허용오차를 둬라.**
"보이는 것과 판정이 어긋나는" 것은 조용히 틀리는 것만큼 나쁘다 — 화면을 못 믿게 만든다.

## T88. 분기가 넘어가면 직전 분기 LLM 분석이 화면에서 **사라진다** `[HD 2026-08-22 실측]`

종목 상세는 `getAnalysis(code, 스크리너_평가분기)`로 분석을 읽는다. 그런데 분석은
게이트 통과 상위만 돌리므로(비용 설계), 새 실적이 들어와 **평가 분기가 옮겨가면**
직전 분기 분석이 조회되지 않아 **"아직 분석하지 않았다"**가 뜬다.

실측: 분석 보유 358종목 중 **63종목**이 그 상태였다. 분석이 DB에 멀쩡히 있는데도.

**게다가 그 63종목이야말로 내러티브를 검증할 수 있는 유일한 대상이다** —
분석 이후 실제 실적이 나온 종목이기 때문이다. 버리면 검증 기능이 **영영 안 돈다**
(평가 분기 = 최신 분기이므로 대조할 뒷분기가 존재하지 않는다).

→ 평가 분기 분석이 없으면 **가장 최근 분석으로 물러서고**, 어느 분기 것인지를
화면에 밝힌 뒤 그 분기 기준으로 검증한다.

**교훈: "최신 분기 것만 보여준다"는 규칙은 최신이 갱신되는 순간 데이터를 숨긴다.**
그리고 **검증 로직의 기준 시점은 평가 분기가 아니라 "분석이 실제로 본 분기"**여야 한다 —
여기를 틀리면 검증이 가능한 종목에서 정확히 검증이 꺼진다.

## T89. 부호 검사가 인사이트 ①에만 있고 ②에는 없어 **두 조언이 서로 어긋났다** `[HD 2026-08-22 실측]`

결과 추적 화면이 같은 시즌에 대해 이렇게 말했다.

```
① 초과수익이 가장 컸던 구간은 발표 후 20일  → "확인 후 진입이 유리했다"
② 발표 전이 발표 후보다 좋았다              → "발표 전 선제 진입 비중을 늘려라"
```

②의 실제 숫자는 **발표 전 −1.70%p vs 발표 후 −2.36%p** — 둘 다 지수를 못 이겼다.
덜 나쁜 쪽은 **비교 결과일 뿐 전략이 아니다.**

①에는 "중앙값이 음수면 '가장 컸다'고 말하지 않는다"는 부호 검사가 **주석까지 달려**
들어 있었는데, 같은 파일의 ②에는 없었다. **한 곳만 고친 방어는 재발한다**(T55와 같은 모양).

→ ②에 `bothLost` 검사를 넣어, 둘 다 음수면 진입 시점을 권하지 않고
"타이밍이 아니라 대상을 좁혀라"로 바꿨다.

**교훈: 같은 종류의 방어는 클래스 전체에 넣어라.** 그리고 화면에 조언이 여러 개 뜨면
**서로 모순되는지를 반드시 같이 읽어라** — 각각은 맞는데 나란히 놓으면 틀린 경우가 있다.

## T90. 두 **실행**을 비교하면 로직 차이가 아니라 **데이터 갱신분**을 본다 `[HD 2026-08-22 실측]`

G4(OPM 상승) 게이트를 넣고 효과를 이렇게 보고했다.

```
발송 대상  107  →  100    "G4가 7종목을 줄였다"
```

**틀렸다.** 107은 **2026-08-21 실행값**이고 100은 오늘 실행값이다.
그 사이 `price_snapshots`가 갱신돼 PRI가 바뀌었고, 등급은 스코어×PRI 교차 판정이므로
**G4와 무관하게** 등급이 움직였다.

같은 원자료에 **G4만 켜고 끄자** 이렇게 나왔다.

```
게이트 통과   297 → 269   (−28)   ← 여기는 진짜 G4 효과
발송 대상     100 → 100   (변화 없음)
```

**7은 전부 시세 갱신분이었다.** G4가 알림에 미친 영향은 **0이다.**

**왜 0인가 (이것도 몰랐던 사실):** OPM이 내려가면 스코어 B1(OPM YoY · 14점)이 0이 된다.
그래서 G4가 떨어뜨리는 종목은 **애초에 스코어가 낮다** — 실측 28종목의 스코어
중앙값 38.5 · **최고 63.8**로 ★/○ 문턱(75)에 닿는 종목이 하나도 없었다.
G4는 스코어와 상당 부분 **중복**이고, 실질 효과는 목록·매트릭스에서 28종목이 빠지는 것이다.

**어떻게 재야 하나:** 로직 효과는 **같은 입력에 두 로직**을 돌려서만 잴 수 있다.
`screen_results`는 `--save`로 덮어써지므로 "이전 판정"이 DB에 남지 않는다 →
원자료를 다시 읽어 **판정만 두 벌 만들어** 비교한다. G4를 뺄 때는 입력에서
`opm_yoy_delta`를 지우면 안 된다 — 그러면 `g4`가 `None`이 되어 `passed`가
**판정 불가로 오염된다.** `(g1, g2, g3)`만으로 종합 판정을 **재조립**해야 한다.

**교훈: "이전 → 이후" 숫자를 댈 때 그 둘이 같은 입력에서 나왔는지 먼저 확인하라.**
날짜가 다른 두 실행을 비교하면 **로직 변경의 공로(또는 책임)를 데이터 갱신이 가져간다.**
이 프로젝트처럼 시세가 매일 갱신되고 등급이 시세에 의존하면 특히 그렇다.

## T91. Anthropic tool 스키마는 `minItems`를 **0과 1만** 받는다 `[HD 2026-08-22 실측]`

트리거를 "발생 가능성이 있는 것 전부" 받으려고 하한을 스키마에 넣었다.

```python
"trigger_list": {"type": "array", "minItems": 2, ...}
```

배치를 돌리자 **호출이 전부 400으로 죽었다.**

```
BadRequestError: 400 invalid_request_error
  tools.0.custom: For 'array' type, 'minItems' values other than 0 or 1
  are not supported (got: [2, 5])
```

3건 시도 → **3건 전부 실패 · 분석 0건.** (비용은 $0였다 — 요청이 거부돼 생성 자체가 없다.)

**왜 위험한가:** 이 버그는 **파이썬 쪽에서 아무 문제가 없다.**
스키마는 멀쩡히 직렬화되고, `json.dumps`도 통과하고, 기존 테스트 555건도 전부 초록불이었다.
**실제로 API를 불러야만 드러난다.** 그대로 뒀다면 밤 `llm_batch.yml`이
**매 종목마다 400을 맞으며 세 시간을 통째로 날렸을 것이다** — 게다가 배치는
실패를 세고 넘어가므로 "실패 269건"이라는 로그만 남기고 조용히 끝난다.

**고치는 법:** 개수 요구는 **스키마가 아니라 SYSTEM_PROMPT 문장**으로 한다.
실제로 프롬프트의 11종 체크리스트만으로 충분했다(아래 실측).

**회귀 방지:** `tests/test_cost_guard.py::test_schema_has_no_unsupported_array_bounds`가
`$defs` 안까지 훑어 `minItems ∉ {0,1}`과 `maxItems`를 전부 막는다.
그리고 **검사기가 실제로 걸리는지를 별도 테스트로 검증한다**(T54) —
`minItems: 2`를 일부러 넣어 실패하는 것까지 확인했다.

**교훈: 외부 API의 스키마 제약은 로컬 테스트가 잡지 못한다.**
스키마를 고쳤으면 **반드시 1건이라도 실제 호출로 확인**하라.
그리고 모델에게 개수를 요구할 때는 스키마보다 프롬프트가 안전하다 —
스키마는 거부당하면 전부 죽지만, 프롬프트는 최악이라도 덜 지켜질 뿐이다.

### 곁다리 실측 — 프롬프트만으로 시나리오가 좋아졌나 (3건)

| | 옛 프롬프트(382건) | 새 프롬프트(3건) |
|---|---|---|
| 시나리오 조건 평균 길이 | 41.6자 | **55자** |
| 조건에 숫자 포함 | 96.0% | **100%** |
| 트리거 평균 개수 | 3.7 | 3.0 |

조건이 "3Q 매출 1,800~2,000억, OPM 1~3%"처럼 **다음 분기 실적과 직접 대조 가능한**
형태로 바뀌었고 확률 합도 3건 모두 정확히 1.00이었다.
**트리거 개수는 늘지 않았다** — 다만 표본 3건이고 하필 성숙 산업 중견주(화학·제약·
전자부품)라 CAPA 증설·지역 진출 같은 이벤트가 실제로 없는 종목들이다.
**3건으로 트리거 다양성을 판정하지 마라.**

## T92. `price_snapshots.per`는 **직전 사업연도 EPS 기준**이라 가속 종목에서 항상 틀린다 `[HD 2026-08-23 실측]`

사용자가 "PER이 잘못된 숫자로 계속 나온다"고 지적해 파고들었다. 계산으로 대조하니:

| | 스냅샷 PER | 2025 연간 순이익 기준 | **실제 TTM(최근 4분기) PER** |
|---|---|---|---|
| 고영 | 131.63 | 130.8 ← **일치** | **40.5** |
| 삼화콘덴서 | 75.12 | 74.7 ← **일치** | **48.8** |
| 삼성전자 | 42.89 | 36.4 | **10.9** |

스냅샷 값은 **직전 사업연도 EPS 기준 후행 PER**이다. 실적이 급가속하면 분모가
1년 낡아 2~3배 과대평가된다 — 그리고 **이 시스템은 정확히 그런 종목만 고른다.**
왜곡이 항상 최악으로 걸리는 구조다.

**어디가 틀렸나:** 대시보드 밸류에이션 카드는 이미 올바로 재계산하고 있었다
(`valuation.ts`). 텔레그램도 마찬가지였다(`notify/run.py`). **LLM 입력 경로만**
`price` 딕셔너리를 통째로 JSON 덤프하면서 후행 `per`을 함께 넘기고 있었다.
모델은 그 숫자를 그대로 인용해 "PER 102배" 같은 본문을 썼고, 그게 화면에 남았다.

→ `src/finance/valuation.py`를 만들어 `valuation.ts`와 **같은 규칙**으로 다시 재고,
LLM 입력에서 후행 `per`을 **제거**한 뒤 두 배수를 라벨과 함께 준다.
화면의 '주가 위치' 카드도 **화면이 계산한 값**을 크게 띄우고, 본문 숫자와 다르면
어느 쪽이 맞는지 밝힌다(옛 분석 본문에는 틀린 숫자가 그대로 남아 있기 때문이다).

**곁다리로 드러난 것:** `analysis/run.py`의 `FUND_COLUMNS`에 **`np`가 빠져 있었다.**
그래서 새로 만든 TTM PER이 처음엔 **전 종목 '계산 불가'**로 나왔다 — 데이터는
멀쩡히 있었다. 컬럼 하나가 빠지면 지표 하나가 조용히 사라지는 이 모양은
A3(`ttm_op`)에서도 똑같이 났다. **파생 지표를 추가할 때는 원자료 컬럼부터 확인하라.**

**교훈: 외부에서 받은 배수를 그대로 쓰지 마라.** 분모가 언제 기준인지 모르면
그 숫자는 검증 불가능하다. 이미 올바른 계산이 다른 곳에 있는데 한 경로만
원본을 쓰고 있으면, **그 경로만 조용히 틀린다.**

## T93. 트리거를 "이벤트만"으로 조이면 **목록이 통째로 비어 버린다** `[HD 2026-08-23 실측]`

"3Q 매출 2,000억 상회 여부" 같은 결과형 트리거를 없애려고 프롬프트에
**"실적 발표 그 자체는 트리거가 아니다"**를 넣었다. 그러자 삼화콘덴서에서
**트리거가 0건**으로 돌아왔다(검증 경고 후 재시도했는데도 0건).

**근본 원인은 프롬프트가 아니라 입력이다.** `AnalysisInput.excerpt`가
**항상 `None`**이다 — `build_input`이 공시 원문 발췌를 채우지 않는다.
모델이 받는 것은 8분기 숫자표뿐이라 **CAPA 증설·신제품 출시·고객사 협업·판가 인상을
알 방법이 자체가 없다.** 숫자만 주고 사건을 쓰라고 하면 선택지는 둘뿐이다:
지어내거나, 비우거나. 모델은 비웠다 — **그게 정직한 쪽이다.**

→ ① 프롬프트에 "목록을 통째로 비우지는 마라 — 사건을 특정할 수 없으면 그 사실을
`how_i_could_be_wrong`에 밝히고 관측 가능한 확인 지점을 `kind: "실적확인"`으로 담아라"를 추가.
② 화면에 **빈 상태를 설명하는 카드**를 넣었다 — 그냥 사라지면 "분석이 덜 됐나"로 읽힌다.

**교훈: 출력 품질을 프롬프트로만 밀어붙이기 전에 입력에 그 정보가 있는지 확인하라.**
없는 정보를 요구하면 모델은 지어내거나 침묵한다. 둘 다 원하는 결과가 아니다.
**이벤트 기반 트리거를 제대로 받으려면 공시 발췌(2,000자, ADR 4가 허용)를 실어야 한다.**
